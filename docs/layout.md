# 折本の面付けはなぜこの並びになるのか

このプロジェクトの心臓部は `src/orihon/layouts.py` です。
ここには「どのマスに何ページ目を、どの向きで置くか」の表しか書いていません。
折り線・切り込み・妥当性チェックはすべてその表から導かれます。

## 1. 用語

1 枚の紙を格子状に分けた 1 マスを **パネル (panel)** と呼びます。
パネル 1 つが折本の 1 ページになります。

隣り合うパネルの境界線は 2 種類しかありません。

* **折り線 (fold)** … そこで紙を折る
* **切り込み (cut)** … そこにハサミを入れる

## 2. 片面刷りの折本が満たすべき条件

折本は 1 枚の紙の**片面だけ**を使って本にします。
つまり、できあがった本を開いていくと、印刷面がずっと表に出たまま
①→②→…→⑧ と続き、最後の⑧の裏がまた①（表紙）に戻ります。

紙の上でこれを言い換えると:

> **条件A** ページ①→②→…→⑧→① が、パネルの上を**一筆書きで一周**している
> （グラフ理論でいうハミルトン閉路）。

さらに、折り目の向きによって天地が決まります。

> **条件B** **左右**に隣り合うパネルは向きが**同じ**
> （縦の折り線は紙を裏返さないため）
>
> **条件C** **上下**に隣り合うパネルは向きが **180 度ちがう**
> （横の折り線は紙を裏返すため）

条件Bと条件Cから、パネルの回転角は「段」だけで決まります。
最下段を 0 度とすると、1 段上がるごとに 180 度ずつ反転します。
`_auto_rotations()` がやっているのはこれだけです。

## 3. 切り込みは「計算で出てくる」

格子の内部にある境界線をすべて列挙し、
そのうち**ページ順が連続している 2 つのパネルの間にあるもの**を折り線とします。
残りは、どうやっても折り目にならない線です。
そこは切り離さないと本になりません ＝ **切り込み**です。

キンコーズの図6 のレイアウトで実際に計算してみます。

```
      列1    列2    列3    列4
上段   7↓     6↓     5↓     4↓      ← すべて 180 度回転
      ─────┼══════┼══════┼─────
下段   8      1      2      3       ← そのまま
```

内部の境界線は 10 本（縦 6 本＋横 4 本）。
ページの環は ①-②-③-④-⑤-⑥-⑦-⑧-① の 8 本。

| 境界 | 両側のページ | 連続？ | 判定 |
|---|---|---|---|
| 下段 列1\|列2 | 8 と 1 | ○（環の閉じ目＝背） | 折り線 |
| 下段 列2\|列3 | 1 と 2 | ○ | 折り線 |
| 下段 列3\|列4 | 2 と 3 | ○ | 折り線 |
| 上段 列1\|列2 | 7 と 6 | ○ | 折り線 |
| 上段 列2\|列3 | 6 と 5 | ○ | 折り線 |
| 上段 列3\|列4 | 5 と 4 | ○ | 折り線 |
| 中央 列1 | 7 と 8 | ○ | 折り線 |
| **中央 列2** | **6 と 1** | **×** | **切り込み** |
| **中央 列3** | **5 と 2** | **×** | **切り込み** |
| 中央 列4 | 4 と 3 | ○ | 折り線 |

残った 2 本、**中央の横線のうち真ん中 2 マス分**が切り込みになりました。
これは図6 の中央に描かれているひし形（開いた切り込み）と一致します。

`Layout.cut_edges()` はこの表そのものです。手で位置を書いていません。

## 4. 背（せ）と小口（こぐち）

同じ計算から、どの折り線が**背**（本の綴じ側）になるかも分かります。

* ページ⑧と①の間 ＝ 本の外側を一周する折り目 ＝ **背**
* ページ②と③、④と⑤、⑥と⑦ ＝ 見開きの中央 ＝ **背**
* ページ①と②、③と④、⑤と⑥、⑦と⑧ ＝ 紙の端 ＝ **小口**

図6 では表紙①が下段の列2 にあり、その背は左隣（⑧との境）にあります。
つまり表紙を手前にして持つと綴じ目が左＝**左綴じ**（横書き向き）です。

縦書きやマンガのように右綴じにしたいときは、列の並びを左右反転すれば済みます。
`orihon8-right` は `_mirror()` でそれを作っています。
反転しても条件A〜Cはそのまま成り立つので、折り方も左右対称になるだけです。

## 5. 検証が効いていること

`Layout.validate()` は条件A〜Cを機械的に検査します。
たとえば次の表は「①と②が離れている」ため登録できません。

```python
>>> Layout(name="bad", title="bad",
...        pages=((1, 3), (2, 4)),
...        rotations=((180, 180), (0, 0))).validate()
LayoutError: bad: 連続するページが隣り合っていません (1-4, 2-3)。
             折り線が作れないため、この面付けでは折本になりません。
```

回転角が条件Cに反していても弾かれます。

```python
>>> Layout(name="bad", title="bad",
...        pages=((3, 2), (4, 1)),
...        rotations=((0, 0), (0, 0))).validate()
LayoutError: bad: 横の折り線 (0,0)-(1,0) の回転差が 0 度です（180 度である必要があります）
```

同梱の全プリセットはテスト (`tests/test_layouts.py`) で毎回検証しています。

## 6. 用紙ごと 90 度倒す（横長原稿のために）

条件Bと条件C（左右は同じ向き／上下は 180 度ちがい）は、実は
**「仕上がった本を立てて持ち、背を左右どちらかに置いて読む」**ことを前提にしています。
本を横に倒して、背を上に置き、ページを上にめくる本（天綴じ）にすると、
縦と横の役割がそっくり入れ替わります。

`Layout.turn` がこれを表します。

| `turn` | 縦の折り線 | 横の折り線 |
|---|---|---|
| `0`（立てて読む） | 回転差 0 度 | 回転差 180 度 |
| `90`（倒して読む） | 回転差 180 度 | 回転差 0 度 |

`validate()` の判定は 1 行で書けます。

```python
expected = 0 if (edge.orientation == "v") ^ (self.turn == 90) else 180
```

`rotate90()` は、あるレイアウトの**紙そのものを時計回りに 90 度倒した**
レイアウトを機械的に作ります。マス `(r, c)` は `(c, 行数-1-r)` へ移り、
回転角は一律 270 度足されます。

紙は同じものなので、**折り線も切り込みも位置が 90 度回るだけ**です。
これはテストで確かめています（`tests/test_landscape.py`）。

```
orihon8（A4 横・4列2段）          orihon8-landscape（A4 縦・2列4段）
┌───┬───┬───┬───┐                  ┌───┬───┐
│ 7 │ 6 │ 5 │ 4 │                  │ 8 │ 7 │
├───┼═══┼═══┼───┤   ── 90度 ──▶    ├───┼───┤
│ 8 │ 1 │ 2 │ 3 │                  │ 1 ┃ 6 │
└───┴───┴───┴───┘                  ├───┼───┤
   パネル 74×105mm（縦長）          │ 2 ┃ 5 │
                                    ├───┼───┤
                                    │ 3 │ 4 │
                                    └───┴───┘
                                    パネル 105×74mm（横長）
```

回転後は、**表紙（ページ1）の回転角が 0 度になるよう全体をそろえます**。
全パネルに同じ角度を足しても隣同士の差は変わらないので、折本としての
成立性には影響しません。変わるのは「本をどちら向きに持って読むか」だけです。
ページ1を 0 度にそろえておくと、横長のパネルには横長の原稿が
そのまま（回転なしで）入ることになります。

綴じ位置も一緒に回ります。左綴じ → 天綴じ、右綴じ → 地綴じです。

## 7. 面付けエンジン側の自動回転

レイアウトの回転角（`Layout.rotations`）は**紙の折り方**が決めるもので、
原稿をパネルの中でさらに回すかどうかは別の話です。パネルごとに独立して
決められるので、折り方には影響しません。

`ImposeOptions.auto_rotate`（既定 `True`）が有効なとき、
面付けエンジンは各ページについて「そのまま」と「さらに 90 度回す」の
両方でパネル面積の占有率を計算し、**2% 以上よくなる場合だけ**回します。
2% の余裕を設けているのは、ほぼ正方形の原稿がページごとにバラバラの
向きになるのを防ぐためです。

```python
def _fit_coverage(panel_w, panel_h, src_w, src_h):
    scale = min(panel_w / src_w, panel_h / src_h)
    return (src_w * scale) * (src_h * scale) / (panel_w * panel_h)
```

この占有率は `ImposeResult.coverage` として毎回報告されます。
低いまま（55% 未満）で、かつ 90 度倒した対のレイアウト（`Layout.sibling`）が
登録されていれば、そちらを使うよう案内します。

用紙の向きの自動判定（`_choose_landscape`）も、`auto_rotate` が有効なときは
原稿を寝かせた縦横比を候補に加えて判定します。

## 8. 「用紙に合わせて印刷」された原稿

仮想プリンタ経由でスライドを受け取ると、アプリ側がスライドを用紙に合わせて
描くため、周囲に大きな単色の帯が付いてくることがあります。この帯は
パネルの占有率だけを見ても気づけません（帯まで含めてぴったり収まってしまうため）。

`detect_uniform_bands()` は、ページを低解像度（既定 48dpi）のグレースケールに
描き出し、**全幅が同じ色の行**が上下から何行続くか、**全高が同じ色の列**が
左右から何列続くかを数えます。これが帯です。

* 1 辺につき最大 45% までしか削りません（ほとんど白紙のページ対策）
* ふつうの文書の余白は「全幅が単色」にならないことが多く、削られません
* 帯が大きいときは、`trim` が無効でも警告だけは出します

## 9. 例外：蛇腹折りと N-up

`kind` が `"foldbook"` 以外のレイアウトは、条件が少し変わります。

* **`accordion`（蛇腹・経本折り）**
  段ごとに紙を切り離してから、山折り谷折りを繰り返して貼り合わせます。
  段をまたぐつながりは折り線ではなく「貼り合わせ」なので、環にはなりません。
  各段が左から連番であることだけを検査し、段の境界はすべて切り離し線になります。

* **`grid`（N-up）**
  折らずに切り離すだけのチラシ面付けです。折り線は存在せず、
  内部の境界はすべて切り取り線になります。

## 10. 実際の配置

面付けエンジン (`src/orihon/impose.py`) は、決まった表に従って
PyMuPDF の `show_pdf_page()` で原稿を各パネルへ貼り込みます。

* パネルの矩形から `safe_margin_mm` だけ内側に入れた領域に配置します。
  プリンタの印字できないフチで絵柄が切れるのを防ぐためです。
  格子そのものは紙いっぱいに取るので、**折り位置は必ず紙のちょうど半分・4 等分**になります。
  紙の端を揃えて折れば正しい位置に折り目が付きます。
* `orientation` が `auto` のときは、パネルの縦横比が原稿の縦横比に
  いちばん近くなる用紙の向きを選びます。
  そのため `orihon8`（4 列×2 段）は A4 横、`orihon4`（2 列×2 段）は A4 縦、
  `orihon8-landscape`（2 列×4 段）は A4 縦になります。
* 原稿のページ数がパネル数に満たない分は白紙のまま残します
  （`fill="repeat"` にすると先頭から繰り返して埋めます）。
* パネル数を超える分は、次の用紙＝別の 1 冊になります。
